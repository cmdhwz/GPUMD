# GPUMD interface-analysis source audit

Audited checkout: `feature/interface-phonon-dynamics`, based on commit `2c93346f` (local `GPUMD-master`, 2026-10-24). This is a source audit only; no build or simulation has been run.

## Findings by requested capability

| Capability | What exists and actual input | Potential / NEP support | Partition support | Reuse and gap |
|---|---|---|---|---|
| Langevin NEMD heat baths | `ensemble heat_lan T tau_T delta_T source_group sink_group`; optional 12 fractional-region bounds are accepted in `src/integrate/ensemble_lan.cu::parse`. `T_hot=T+delta_T`, `T_cold=T-delta_T`. The group form addresses grouping method 0. | The thermostat acts on velocities and is force-model independent, so it can be used with NEP. | Two fixed group IDs or two fractional regions; not an arbitrary dynamically binned material definition. | Reuse the existing bath counters. **Sign correction required:** counters mean energy transferred from the system to the baths. Heating the source decreases its counter (negative); cooling the sink increases its counter (positive). The task text's proposed positive-hot/negative-cold interpretation is the opposite of the source code. See `integrate_heat_lan_half` and `integrate_heat_lan_region_half`. |
| NHC / BDP heat baths | `ensemble heat_nhc ... source_group sink_group` and `ensemble heat_bdp ... source_group sink_group` are parsed in `src/integrate/ensemble_nhc.cu` and `src/integrate/ensemble_bdp.cu`; both maintain the same two system-to-bath energy counters. | Force-model independent; NEP compatible. | Group IDs in grouping method 0. | Reuse only for bath-energy diagnostics; preserve each integrator's own counter convention and avoid assuming stochastic trajectories have identical stepwise exchange. |

Existing temperature does not remove group/bin drift, apply local DOF corrections, or use the fixed/moving-group exclusions documented by the integrator. Add a separate optional profile output for current-position bins and explicit DOF handling. |
| `compute` heat-current components | `jp` is the per-atom virial tensor contracted with velocity; `jk` is per-atom total energy times velocity (`src/measure/compute.cu::find_per_atom_jp` and `find_per_atom_jk`). | NEP provides per-atom virial and site energy. | Sums by existing grouping method. | Useful as the existing volumetric/current diagnostic. A group sum of `jp`/`jk` is not the strict energy crossing an internal plane. Do not relabel it as plane flux. |
| Spectral heat current | Existing `compute_shc` keeps its virial-current definition. ## Units and thermostat sign

| Quantity | Source convention |
|---|---|
| Length, position, box | Å |
| Mass | atomic mass unit |
| Potential energy / bath exchange | eV |
| Force / virial | eV/Å / eV |
| Time step in `run.in` | input is fs; `src/main_gpumd/run.cu::parse_time_step` divides by `TIME_UNIT_CONVERSION` before integration |
| Internal time | GPUMD natural time; `TIME_UNIT_CONVERSION=10.18051 fs` in `src/utilities/common.cuh` |
| Temperature constant | `K_B=8.617343e-5 eV/K` in `src/utilities/common.cuh` |
| XYZ velocity | Å/fs (`dump_xyz.cu` converts from natural-time velocity) |
| SHC time/frequency | `shc.out` documents ps and THz in `src/measure/shc.cu` |

For the legacy `compute.out` bath columns under `heat_lan`, let `s_hot` and `s_cold` be the raw slopes of the source and sink counters (eV/ps after time conversion). The positive-into-system convention requested by the analysis is `P_hot=-s_hot` and `P_cold=-s_cold`; therefore `P=(s_cold-s_hot)/2`. The raw source counter should decrease while the hot source supplies energy, and the raw sink counter should increase while the cold sink receives energy. This sign conclusion is source-derived; the required independent NEMD sign regression has not yet been run.

`compute.out` contains no time column or header. With constant `time_step`, reconstruct sample times from the `compute` intervals and the input timestep, converting input fs to ps. The legacy `compute` path writes cumulative counters, so fit each counter across the selected steady-state window. `heat_hybrid` has a separate variable-length counter path and must not be parsed as the two-column `heat_lan` case.

## Implementation boundary from this audit

1. M0 provides a shared fixed reference mapping; M1 consumes it for a native online temperature/potential profile and retains the older dynamic 17-column profile. The Python thermal-resistance reader remains pending and is incompatible with the new 19-column profile.
2. M2 provides spatial per-atom VACF and an explicitly unnormalized one-sided VDOS spectrum over selected fixed bins and types. It does not implement modal projections.
3. M3 has an opt-in strict plane-flux/SHC implementation in the ordinary NEP large-box path. The independent real-NEP runtime/finite-difference fixture and GPUMD runtime fixture are present but unbuilt and unrun, so M3 remains pending validation. Existing `compute_shc`, grouped `jp`, and grouped `jk` retain their existing definitions.
4. The native support and remaining boundaries for M4-M8 are listed below. Existing inputs and force paths are reusable infrastructure; their presence does not mean the requested postprocessing workflows are complete.

## M4-M8 native delivery boundary

| Module | Existing native support and input path | Actual gap in this pass |
|---|---|---|

| M5 wavepacket propagation and harmonic reference | `model.xyz` accepts per-atom initial velocities through its extended-XYZ `properties=...:vel:R:3` field (`src/model/read_xyz.cu::read_xyz_line_2` and `read_xyz_in_line_3`); `src/main_gpumd/velocity.cu::Velocity::initialize_cpu` preserves supplied velocities, and `src/integrate/ensemble_nve.cu::Ensemble_NVE::compute1/compute2` supplies NVE. ## Verification status

The unified `tests_regression/interface_native` C++14/CMake suite registers M0 geometry, M1 profile math, M2 VACF normalization, and M3 math/time/statistics tests without CUDA. The separate M3 CUDA target still tests real NEP finite differences and force invariance. Runtime M3 fixtures use a deterministic distorted diamond-carbon input with two complete blocks and an empty selected plane; they are software-path checks, not material validation. These native tests and the real GPUMD input have not been built or run: no CUDA/C++ compiler or GPUMD executable is available in this environment. Python tests were not changed or run. No GPU simulation or scientific acceptance is claimed.

## Work not implemented

M3 native code and fixtures now exist for the supported regular-NEP large-box path, but compilation and physical consistency are unverified. M4 analysis, M5 wavepacket/paired-ensemble workflow, M6 IFC2 residual projection and modal power, M7 lifetime/MFP/recovery analysis, and M8 mass-scaling mismatch analysis remain unimplemented. Existing GPUMD SHC, grouped heat current, legacy VDOS, FCP order-2 force, model.xyz velocities, and per-atom mass inputs retain their own definitions. The Python interface-analysis reader remains unfinished and incompatible with the native profile-v3 and VACF/VDOS/SHC schemas.
